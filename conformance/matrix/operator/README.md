# operator matrix

Operator lowering across the `op × width/sign × wrapper` grid where the
path-parity / result-type bugs live (Code-Red-2 Class C; `plan-code-red-2.md`
§3.3). Coordinate-addressed:

    conformance/matrix/operator/<op>/<wrapper>/<type>.bn   (+ .expected)

Generated by `conformance/gen-operator-matrix.py`.

## Scope

This is the **targeted** layer — the confirmed/predicted-gap sub-grids — not the
full operator Cartesian (`scalar`/`scalar-diff` already cover sub-word arithmetic
*values*). Currently the **unary**, **compound-assign**, **eq-reject**, and
**rel** (relational operand-position) sub-grids; the broader pairwise binary
sample is a planned follow-up (§3.3).

### rel sub-grid

`relop {<, >, <=, >=} × operand-position {lit-left, lit-right} × signed type
{int, int8}`. The untyped-int literal on the LEFT of a signed operand must use a
SIGNED comparison (`5 < x` for `x = -1` is `false`); `b54c9fdf` fixed a bug that
made it unsigned. The `lit-left` cells guard that fix; `lit-right` is the control.
**All green** on every backend — a regression net for the literal-position
signedness.

### Unary sub-grid

`op {neg, bitnot} × type {int8/16/32/64, uint8/16/32/64} × wrapper {plain,
named}`. Assertion: the unary result equals the spec value at the operand's width
(printed `cast(int, …)`).

### Compound-assign sub-grid

`op {shl-overshift (`<<=`), shr-overshift (`>>=`), add (`+=`)} × lvalue-form
{ident, field, index}`. The path-parity question: does a guard/fix applied on the
`ident` lvalue reach the field/index forms? Assertion: the compound-assigned
result equals the spec value (an overshift count ≥ width → 0). **All green** — the
overshift guard (`fa265629`) reaches every lvalue form, and the `add` controls
confirm compound-assign works through field/index. A pure regression net.

### eq-reject sub-grid (`.error` cells)

`==` on each NON-comparable operand `{raw-slice, managed-slice, func-value,
iface, struct, array}` must be REJECTED at the checker.  These are negative
(`.error`) cells: green = the checker correctly rejects.  **All green** on every
backend (front-end reject).  Slices, interface values, and function values are
never comparable.  A plain struct / array of comparable fields IS now comparable
(lowered field/element-wise — see `spec/13-expressions/015,016` and
`spec/07-types/044`), so the `struct` / `array` cells use an aggregate that
transitively CONTAINS a slice field (e.g. `struct { n int; v @[]int }`), which
stays rejected ("this struct/array is not comparable").

## Current state

All green. The **named sub-word negation** cells — `neg/named/{int8,uint8,
int16,uint16,int32,uint32}` — were the live defect (unary minus on a `TYP_NAMED`
sub-word int emitted `sub i64 0, %i8`, which clang rejected, because the
`gen_expr` MINUS arm gated on `TYP_INT` and never peeled `TYP_NAMED`; LLVM-only,
the VM/native backends tolerated the mis-typed IR). That is now fixed (binate
`3c609caf`, peel the named wrapper in the MINUS arm like `~` already did), so the
cells are no longer xfailed. The named `~`/`-` asymmetry the matrix swept the
wrapper axis to catch (the earlier unary-minus fix `fce07ccd` was strictly weaker
than the `~` fix it claimed to mirror) is closed.
