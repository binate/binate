# Scalar-diff matrix (differential value-correctness)

A property-based **differential** harness for scalar **shifts** and
**conversions** — the exhaustive-volume layer beneath the curated
`../scalar` matrix (see `../README.md`). Generated by
`conformance/gen-diff-scalar.py`.

    conformance/matrix/scalar-diff/shl|shr/<width>/<sign>.bn   shifts
    conformance/matrix/scalar-diff/int-to-float/<width>/<sign>.bn
    conformance/matrix/scalar-diff/float-to-int/<width>/<sign>.bn
    conformance/matrix/scalar-diff/int-cast/<width>/<sign>.bn
    conformance/matrix/scalar-diff/float-cast/roundtrip.bn

## Why this exists alongside `../scalar`

`../scalar` tests a few hand-picked values per op, so it only catches a bug
*at a value someone thought to write* — a shift-by-≥-width bug hid for
exactly that reason (the matrix only used in-range counts). This harness emits
a **fixed, seeded value set** per coordinate — every type/op boundary plus a
deterministic pseudo-random sample — so a whole region of the input space is
swept, not a point.

## The oracle is the spec, not a backend

Each `.expected` is the **spec-mandated** answer, computed by the generator at
full precision per the spec's operator and type-conversion rules, independent of
any backend. This is the key property: a value wrong on *every* backend (a
spec-divergence — the shift-bug class) is still caught, because every backend
then fails the cell vs the reference. An LLVM-as-oracle differential (compare
the VM against LLVM) would miss it, since LLVM is wrong too.

## Self-checking cells (target-stability)

Each tuple computes the op at runtime — operands live in `var`s, so the
**backend** op runs, not the const-folder — and prints
`cast(int, (computed == spec_expected))`, which is `1` exactly when the backend
matches the spec. The comparison happens at the operand width *in-language*;
only a `0`/`1` is emitted. So a 64-bit result never truncates through
`cast(int, …)` on a 32-bit (arm32/ILP32) target, and a sub-word value never
hits the native sub-word print path — the cell's output is target-stable.
Every `.expected` is therefore a column of `1`s; a `0` on line N means tuple N
(commented in the `.bn`) diverged from the spec. (The trade-off is that a
failure shows *which* tuple, not the wrong value. The comparison families
(`cmp`/`fcmp`) instead print the comparison result directly, so a failure
already shows got-vs-want.)

## What each family asserts

- **shl / shr** — `x OP c` for operand and count `var`s of the same type
  (`../shift-typepair` crosses the count's type). Counts span
  in-range, `0`, `width-1`, `width`, `width+1`, `width+2`, `2·width`,
  `2·width+3`, and a seeded-random value, crossing the overshift edge
  (spec: `<<` / logical `>>` → 0, arithmetic `>>` → sign-fill). `shr` is
  arithmetic for signed types, logical for unsigned.
- **int-to-float** — sign preservation (an unsigned value with the top bit set
  must become a large *positive* float — the signed-convert bug reads it
  negative) plus an exact round-trip `cast(T, cast(F, v)) == v` for every `v`
  representable in the target float (`|v| < 2^24` for `float32`, `2^53` for
  `float64`). Non-representable magnitudes are checked for sign only, never for
  an exact rounded value.
- **float-to-int** — truncation toward zero from exact binary-fraction literals,
  plus a high-bit round-trip: for unsigned dest, `2^(width-1)` (the in-range
  `≥ 2^63` case a signed convert mishandles); for signed dest, `-2^(width-1)`.
- **int-cast** — `cast(DT, v)` to every integer type: value-preserving
  wrap/truncate — source math value reduced mod `2^destwidth`
  and reinterpreted under the dest sign (widening extends by *source*
  signedness; narrowing truncates).
- **float-cast** — `float32 ⇆ float64`: widening is exact; narrowing rounds to
  nearest-even (two exactly-determined cases).
- **arith** (`add`/`sub`/`mul`/`div`/`rem`) — the wrapped (two's-complement)
  result, plus, for add/sub/mul, a second check that consumes the result
  through a width-sensitive `>>` (a backend leaving dirty upper bits diverges
  there even where the direct compare re-narrows). `div`/`rem` truncate toward
  zero with `%`-sign-of-dividend; operands set the high bit (signedness
  dispatch).
- **cmp** — all six relops over operands that cross the high-bit boundary,
  where signed and unsigned disagree; the comparison result *is* the printed
  0/1.
- **fcmp** — all six relops over `{0, -0, ±1, ±Inf, NaN}` (built by `bit_cast`
  from exact IEEE bit patterns), pinning the ordered/unordered semantics (`==`
  and relationals false on NaN; `!=` true on NaN; `+0 == -0`).
- **bitwise** (`and`/`or`/`xor`/`not`) — the masked result; `~` also gets the
  `>>`-consume dirty-bits check (its complement overflows the width).
- **neg** (unary minus `-x`) — the two's-complement negation at the operand
  width, plus the `>>`-consume dirty-bits check (a host-width negation leaves
  dirty upper bits — the unary-minus-result-type bug, the analog of `~`).

## Deliberately excluded (NOT guessed)

The spec says integer cast is "hardware semantics, well-defined" — for
*in-range* values that is target-stable, but the following are
target-dependent or spec-silent, so there is no single expected to assert and
they are left out (documented here rather than given an invented value; a
decision or per-target expecteds would be needed to cover them):

- **out-of-range float→int**, and **NaN / ±Inf → int** (x86 yields `INT_MIN`,
  ARM saturates);
- **float64→float32 narrowing** beyond the two exactly-determined
  round-to-nearest cases;
- **signed `div`/`rem` of min by −1** (the quotient `2^(w-1)` overflows the
  signed range — x86 `idiv` traps `#DE`, ARM `sdiv` wraps), and division by
  zero (the spec makes it a runtime trap, not a value).

## Current state

131 cells / 5623 tuples; no cell carries an `.xfail.<mode>` marker. Among the
defects the cells pin:

- **`~` result type** — IR-gen types `~x` at its operand's type (binate
  `ee7c05ac`); typed as `int`, `~x` on a sub-word int emits invalid IR (`xor i64
  %i8`) and `(~v) >> k` on `uint64` shifts arithmetically. The `bitwise/not`
  cells catch this on the *reference* (LLVM) backend too.
- **`int → float32`** — every `cast(float32, <int>)` must produce a real float32
  value (the float-conversion cells), separately from `float64`, `float32→int`
  truncation, `float32` literals and float32 compare (`fcmp/32`, binate
  `fc11d862`).
- **sub-word results** — a sub-word op's result must be narrowed / sign-extended
  to its type width: sub-word `shl`/`shr` and `int-cast`, signed sub-word
  conversions, signed `arith/{add,sub,mul}/8`, `bitwise/{and,or,xor}/{8,16}`,
  `cmp/{8,16,32}`, and `bitwise/not/{8,16,32}/unsigned` (a 64-bit complement
  ignores the operand width).

On the arm32 modes the 64-bit-width cells exercise 64-on-32 library calls.
