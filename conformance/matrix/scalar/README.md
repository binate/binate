# Scalar matrix

The **sub-word & 64-on-32 scalar value-correctness** (Class 5) member of the
conformance matrix family (`../README.md`). Coordinate-addressed:

    conformance/matrix/scalar/<op>/<width>/<sign>.bn   (+ .expected)

Generated by `conformance/gen-scalar-matrix.py`.

## Axes & assertion

- **op** — three categories, each a distinct way a value can go wrong:
  - arithmetic `add` / `sub` / `mul` — the result overflows the width and is
    consumed DIRECTLY by a width-sensitive shift (no intermediate sized var to
    re-narrow), exposing un-narrowed dirty upper bits;
  - `div` / `rem` — signed (sdiv/srem) vs unsigned (udiv/urem) dispatch on a
    high-bit-set value;
  - `int-to-float` / `float-to-int` — an unsigned int with the top bit set must
    convert to a large positive float, and round-trip back (a signed conversion
    mis-reads it);
  - `shl-overshift` / `shr-overshift` — a shift whose **count is >= the operand
    width** must yield 0 (`<<` / logical `>>`) or sign-fill (arithmetic `>>`) per
    the spec, NOT the masked `count mod width` that
    raw hardware/LLVM produce. The count is a runtime `var` (typed to the
    operand, as Binate requires), exercising the backend shift, not const-fold.
- **width** — the scalar width in bits (8 / 16 / 32 sub-word; 64 = full host
  word, a baseline). `int-to-float` uses 32 (baseline) and 64 (the bug).
- **sign** — `unsigned` / `signed` (arithmetic + div/rem); `int-to-float` is
  unsigned-only.

Assertion: **value correctness** (a refcount-balance check can't see a wrong
value). The `.expected` is the target-independent correct result, computed at
full precision by the generator. LLVM is correct on the sub-word / conversion
cells; the VM and native backends diverge on the buggy ones. The
`shl/shr-overshift` cells were a *spec*-divergence (wrong on every backend incl.
LLVM, since hardware masks the count and LLVM treats overshift as poison); the
guard for that (binate `32fde83d`) has landed, so they now pass everywhere and
stand as the regression guard.

## Current state

Two defects CONFIRMED, both passing on the LLVM modes (`builder-comp`,
`-comp-comp`, `-comp-comp-comp`) and xfailed on the VM modes (`-int`,
`-int-int`, `-comp-comp-int`):

- **dirty upper bits** — the sub-word arithmetic cells (`add`/`sub`/`mul` ×
  8/16/32 × both signs): `execArithOp` computes at the host width without
  narrowing.
- **unsigned int→float** — `int-to-float/64/unsigned`: the VM uses a signed
  conversion (`BC_SITOF`).

Baselines that PASS everywhere (regression nets): the 64-bit arithmetic (no
sub-word narrowing needed), all `div`/`rem` (the signedness dispatch is
correctly fixed), and `int-to-float/32` (a uint32 is zero-extended). The native
lanes (not in the default set) are expected to fail the same buggy cells — add
their xfails when those lanes run. See `claude-todo.md`.
